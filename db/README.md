# GigTask – Freelance Micro-Jobs Marketplace
### Assignment 1 | PostgreSQL + MongoDB Database Implementation

GigTask is a **freelance micro-jobs marketplace** that demonstrates a production-oriented, polyglot database design using **PostgreSQL** for structured transactional data and **MongoDB** for flexible, document-based and geospatial data.

The project includes database schema design, indexes, triggers, stored procedures, materialized views, analytics workflows, realistic mock-data generation, and performance verification using `EXPLAIN` plans.

## Project Overview

The marketplace separates data according to its structure and access pattern:

### PostgreSQL — Structured and transactional data

PostgreSQL manages the core relational entities and transactional logic:

- Clients and their escrow balances
- Freelancers
- Contracts between clients and freelancers
- Wallet audit logs
- Atomic escrow funding through a stored procedure
- Trigger-based audit logging
- Materialized freelancer lifetime statistics
- Window-function-based revenue analytics

### MongoDB — Flexible and high-volume data

MongoDB manages data that benefits from a flexible schema or specialized indexing:

- Freelancer portfolios with optional and varying fields
- Gig reviews and skill tags
- Real-time worker location pings
- Geospatial queries using `$geoNear`
- Review analytics using `$facet`
- Automatic expiry of location pings using a TTL index

## Database Architecture

### PostgreSQL entities

```text
clients
   │
   ├── wallet_audit_logs
   │
   └── contracts ─── freelancers
```

**Main relational tables:**

- `clients` — client identity and available escrow/wallet balance.
- `wallet_audit_logs` — immutable-style records of balance changes generated by the audit trigger and bulk-seeded for performance testing.
- `freelancers` — freelancer identity, base latitude/longitude and availability.
- `contracts` — client–freelancer contracts with budget, status and creation timestamp.

The relational ERD is available in:

- `docs/relational_erd.png`
- `docs/relational_erd.mmd`

### MongoDB collections

| Collection | Purpose |
|---|---|
| `Portfolios` | Flexible freelancer skills, certifications and optional profile information |
| `GigReviews` | Freelancer reviews, ratings, comments and skill tags |
| `WorkerLocations` | High-volume GeoJSON location pings for nearby-worker searches |

A detailed schema map is available in `docs/mongo_schema_map.json`.

### Cross-database relationship

MongoDB documents store the PostgreSQL `freelancers.id` UUID as a string in `freelancer_id`. This provides a logical link between the relational and document databases without requiring cross-database foreign keys.

```powershell
winget install PostgreSQL.PostgreSQL.16
winget install MongoDB.Server
winget install MongoDB.Shell
```

Both install as Windows services and start automatically. PostgreSQL superuser is `postgres` (password set during install).

## Analytics Workflows

### Workflow 1 — Relational transaction processing

The `fund_gig` PostgreSQL stored procedure:

1. Locks the client's row using `FOR UPDATE`.
2. Checks whether the client exists.
3. Verifies that sufficient escrow balance is available.
4. Deducts the contract budget from the client's escrow balance.
5. Creates a new contract with status `FUNDED`.
6. Allows the audit trigger to automatically record the balance change.

This keeps the funding operation transactional and prevents race conditions around the client balance.

---

### Workflow 2 — PostgreSQL window analytics

`sql/06_window_analytics.sql` calculates:

- Daily completed-contract revenue per freelancer
- A rolling 7-day moving average
- Dense ranking based on the moving average
- The top 50 results

The analysis is restricted to completed contracts from the last 30 days.

---

### Workflow 3 — MongoDB nearby-worker search

`mongo/02_workflow3_geonear.js` searches for available workers near a job site using:

- `$geoNear`
- GeoJSON `Point` coordinates
- Spherical distance calculations
- `is_available: true`
- A `2dsphere` index

The workflow returns the nearest five available workers and their distance in metres.

The example job-site coordinates are:

```text
Longitude: 77.2090
Latitude:  28.6139
```

---

### Workflow 4 — MongoDB review analytics

`mongo/03_workflow4_facet.js` analyses reviews from the last 90 days in one aggregation pipeline using `$facet`.

It returns three analytical views simultaneously:

1. **Rating distribution**
2. **Top 10 skill tags**
3. **Top workers by average rating and review count**

## Key Database Features

### PostgreSQL indexes

The project includes:

- A partial unique index preventing a freelancer from having more than one `IN_PROGRESS` contract.
- An index on `contracts.client_id`.
- A partial covering index for recent completed contracts.
- A composite audit-log index on `(client_id, created_at)`.

### Trigger-based auditing

Changes to `clients.escrow_balance` automatically generate records in `wallet_audit_logs` through `trg_wallet_audit`.

### Stored procedure

`fund_gig` encapsulates the escrow funding workflow and uses row-level locking with `FOR UPDATE`.

### Materialized view

`freelancer_lifetime_stats` stores:

- Completed contract count
- Total earnings

A unique index on `freelancer_id` supports `REFRESH MATERIALIZED VIEW CONCURRENTLY` through the `refresh_freelancer_lifetime_stats()` function.

### MongoDB geospatial indexing

`WorkerLocations.location` uses a `2dsphere` index for efficient spherical proximity searches.

### MongoDB TTL

`WorkerLocations.created_at` has a TTL index with `expireAfterSeconds: 7200`, automatically expiring location pings after approximately two hours.

### MongoDB flexible documents

Portfolio documents intentionally contain optional fields such as:

- Certifications
- Years of experience
- Biography
- Hourly rate
- Languages

This demonstrates why a document database is suitable for heterogeneous profile data.

## Assumptions

- Contract status values are `FUNDED`, `IN_PROGRESS`, `COMPLETED` (underscore form of the spec's "IN PROGRESS").
- A client's `escrow_balance` is their available wallet; `fund_gig` deducts from it into a `FUNDED` contract atomically. The audit trigger logs every balance change automatically.
- Workflow 2 (moving average) is computed over the last 30 days and Workflow 4 (review analytics) over the last 90 days, reflecting a rolling analytics dashboard. This also lets both queries use time-bounded indexes instead of full scans.
- `WorkerLocations.freelancer_id` and `GigReviews.freelancer_id` store the PostgreSQL `freelancers.id` UUID as a string, linking the two databases.
- Audit rows are bulk-inserted by the seeder to reach 100k+ volume; live balance changes are logged by the trigger (verified during testing).

## Notes

- The `worker_locations` collection has a 2-hour TTL index, so seeded pings expire. Re-run `mongo_seeder.py` shortly before any demo.
- MongoDB TTL deletion is performed asynchronously by MongoDB, so expiry should not be treated as occurring at the exact second a document reaches the two-hour age.
- Run the SQL scripts in the documented order.
- Run `postgres_seeder.py` before `mongo_seeder.py` because the MongoDB data depends on PostgreSQL freelancer IDs.
- The included performance figures are captured results and may vary depending on hardware, database configuration, cache state and PostgreSQL/MongoDB versions.
